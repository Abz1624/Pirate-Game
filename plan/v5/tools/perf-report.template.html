Rogue Pirates · V5 performance · 1-2 Oct 2026

What slowed the game on a phone, and what changed

I ran the web build on a Pixel 9a over USB, about 50 runs in all: different settings, enemy counts and builds, each measured the same way. I also ran it on this PC's Chrome. Two game systems caused most of the slowdown and the regular freezes. Both are fixed, and phones now get the right texture format.

{{TILES}}

What changed in the game

  • Minimap fog of war. Every newly explored cell made the minimap recompute its whole 160×160 fog texture in one frame, about 14 ms on a desktop and several times that on the phone. These were the regular freezes. It now redraws only the pixels around the new cells (about 100 instead of 25,600). A big reveal, such as a treasure chart, is spread over 8 frames. The result is the same image, pixel for pixel (tested).
  • Enemy health bars. Each enemy's bar was its own canvas with its own script, so 80 enemies meant 80 canvases rebuilt and drawn every frame. All bars now share one canvas, placed by one script and sorted far to near. They use the same prefab, sprites and fill.
  • Phone textures. Unity 6 was quietly resetting the build's texture format, so phones received desktop (DXT) textures, which they cannot use directly. Chrome expanded them, costing over a gigabyte of extra GPU memory. The mobile build now asks for ASTC through the build option, and 163 icons with a fixed DXT format now follow the build too. The desktop build keeps DXT.
  • Build settings. Code is now optimized for speed rather than build time. The benchmark harness exists only in builds made with a separate flag, so normal builds don't include it.

Enemies drive the cost

On the phone, frame time follows the number of enemies alive. With 80 the Pixel 9a fell to the low 20s before the fixes. 260, the current pool cap, is unplayable. This answers the open question about raising the enemy cap: not on phones.

Two systems caused most of it

An Editor profile at 80 enemies pointed at two culprits: per-enemy health-bar canvases (about 60% of what the crowd added) and the minimap's fog rebuild (the spikes). Switching each off on the phone confirmed it. With both off, the slowest 1% of frames fell from about 145 ms to 36 ms.

Settings that barely mattered

Render scale, shadows, post-processing, MSAA and HDR moved the frame rate less than heat did. The phone is limited by the CPU (game code compiled to WebAssembly), not by drawing pixels. The PC quality level was clearly worse. The phone build already uses the Mobile level.

{{SETTINGS_CHART}} {{SETTINGS_TABLE}}

Heat: the same build measured 46 fps at the start of this series and 33 fps 28 minutes later, as the battery went from 38 °C to 42.5 °C. After this, every comparison alternated builds and waited for the phone to cool. A phone in a player's hand will run at the warm figures.

Textures and memory

With DXT textures, Chrome's GPU process on the phone used about 1.3 GB, and the game's WebAssembly heap was 397 MB. With ASTC, the same scene used under 600 MB and 330 MB. The download fell from 111 MB to about 91 MB.

{{TEXTURE_TABLE}}

The heap is still above the 256 MB some older phones allow. Reaching it needs assets streamed in as needed instead of loaded up front, which is a phase of its own (questions 39 and 43). The phone build uses a 512 MB limit until then.

Tried and not kept

  • Lower render scale or the Low tier: no gain (the phone is CPU-bound).
  • A 30 fps cap: steadier frames, but lower frame rate and still frames over 33 ms. Not worth it.
  • WebAssembly 2023: no measured gain, and it stops the game loading on Safari before 16.4. Left off (question 41).
  • Compressing "uncompressed UI art": the art was already compressed. The build report lists uncompressed sizes. Reverted.
  • Dropping the developer Module Lab scene: scenes are tiny, so no gain.

Still open

  • At 80 enemies the remaining cost is real game work: rendering (about 2.4 ms on a desktop) and the enemy simulation (1.4 ms, mostly movement and overlap checks). The next gains would come from the simulation itself.
  • The Galaxy A15 reference phone has a much slower CPU than the Pixel 9a. Expect roughly half these frame rates until it is measured.
